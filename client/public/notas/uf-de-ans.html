Quatro meses depois de concluir um teste técnico básico, decidi voltar ao projeto para evoluí-lo profissionalmente. O que começou como um pipeline linear acabou se tornando uma investigação sobre confiabilidade, arquitetura e qualidade de dados.

A cada etapa de evolução, um novo problema revelava uma limitação que antes permanecia escondida. O ambiente, o banco, o ETL e a camada visual passaram a ser analisados como partes de um mesmo sistema.

O ponto de partida

O projeto original utilizava Python, Pandas, MySQL e uma API REST desenvolvida com FastAPI. Os dados analisados eram demonstrações contábeis públicas da ANS referentes aos três trimestres de 2025.

Naquele momento, o objetivo ainda era extrair, transformar, armazenar e disponibilizar os dados. Quatro meses depois, decidi retornar ao pipeline para investigar como ele poderia se tornar tecnicamente mais confiável, reproduzível e preparado para análises mais profundas.

Quando o ambiente revelou problemas ocultos

A primeira grande etapa foi a containerização com Docker Compose. O ambiente passou a reunir, de forma isolada e reproduzível, o processamento Python, o banco MySQL e a API FastAPI.

A execução dentro dos contêineres revelou problemas na estrutura original do banco. A camada de staging estava sendo utilizada quase como um depósito temporário, sem o nível de validação estrutural necessário.

Reorganizei a staging para cumprir o papel de uma landing zone técnica, alinhando tipos de dados, limpando tabelas e ajustando restrições relacionais para garantir integridade desde a primeira inserção.

O pipeline que dizia “sucesso”

Depois do saneamento do banco, novas inconsistências apareceram em etapas posteriores. O terminal informava que o processo havia terminado com sucesso, mas isso não significava que o resultado estivesse confiável.

Registros nulos, chaves de relacionamento sem validação robusta e transformações silenciosas permitiam que dados inconsistentes avançassem pelo fluxo sem provocar exceções.

Naquele estágio, ainda não havia rastreabilidade detalhada nem logs suficientes para apontar exatamente onde os desvios aconteciam. O ETL precisou ser refatorado de forma investigativa, com validações de preenchimento, filtros preventivos e tratamentos explícitos de tipos de dados.

Um pipeline terminar sem exceções não significa que os dados estejam corretos.

O limite do MySQL

Com o backend mais confiável, avancei para a camada visual usando Streamlit e Plotly. A intenção era explorar os dados por meio de gráficos e análises interativas construídas em Python.

Os endpoints originais da API eram suficientes para consultas simples, mas não entregavam todas as agregações necessárias para análises multidimensionais.

A primeira solução foi transferir parte da inteligência analítica para o MySQL por meio de Views SQL. Porém, as consultas passaram a consolidar e agrupar grandes volumes de registros contábeis por operadora, estado e conta contábil.

O banco, que continuava adequado para armazenar dados estruturados e atender a API, começou a apresentar degradação nas agregações analíticas mais complexas. Isso evidenciou o limite de uma arquitetura que dependia exclusivamente do processamento relacional.

A arquitetura híbrida

Para dividir melhor as responsabilidades, introduzi o Apache Spark no processamento das transformações analíticas mais pesadas.

O MySQL permaneceu responsável pelo armazenamento das dimensões e tabelas finais estruturadas para consumo da API. O Spark assumiu o processamento analítico que anteriormente pressionava o banco.

Também organizei o processamento em módulos, com uma estrutura separada para o núcleo do Spark e para as etapas sequenciais do pipeline. Logs estruturados passaram a registrar o comportamento das execuções dentro dos contêineres.

Com isso, os logs deixaram de ser apenas mensagens de execução e passaram a funcionar como um mapa para investigar falhas, transformações e inconsistências.

A descoberta da UF “DE”

Depois de semanas ajustando Docker Compose, Spark Session, volumes, Views SQL, transformações e tratamento de dados, o pipeline finalmente executou de ponta a ponta.

Quando os gráficos de distribuição por estado foram preenchidos, uma categoria inesperada apareceu: “DE”.

A sigla não correspondia a nenhuma unidade federativa brasileira. Como o valor concentrava registros relevantes, não seria responsável simplesmente removê-lo ou substituí-lo sem investigar.

descoberta

“DE” não era um erro criado pelo ETL. Era uma evidência de uma inconsistência presente nas fontes oficiais brutas da ANS.

Voltei às etapas anteriores do fluxo, comparei os registros processados com os dados de origem e revisei as transformações aplicadas. O pipeline estava preservando e revelando o valor; não havia inventado a inconsistência.

Da inconsistência à Plataforma Analítica

A descoberta mudou a forma como eu enxergava o projeto. O objetivo deixou de ser apenas processar arquivos e disponibilizar tabelas. Passei a pensar em um ecossistema capaz de preservar a origem, organizar domínios, documentar hipóteses e manter rastreabilidade.

Foi nesse processo que começou a nascer a ideia da Plataforma Analítica ANS baseada em domínios: um laboratório autoral ainda em construção, com arquitetura Medallion, camadas Bronze, Silver e Gold, modelagem dimensional e experimentação com PySpark.

A plataforma não nasceu pronta. Ela foi sendo formada a partir das perguntas que os dados colocaram no caminho e das limitações que cada etapa do projeto revelou.

O aprendizado

Essa experiência reforçou uma decisão importante: resultados inesperados não devem ser automaticamente removidos para que a base pareça mais limpa.

Primeiro é necessário compreender a origem, registrar a hipótese e documentar a decisão. Em alguns casos, preservar o dado original é mais responsável do que substituí-lo silenciosamente.

A sigla “DE” acabou se tornando mais do que uma inconsistência cadastral. Ela foi uma das evidências que mudaram minha forma de pensar sobre qualidade, rastreabilidade e arquitetura de dados.

Uma saída inesperada pode ser ruído. Mas também pode ser uma pista sobre o sistema que produziu aquela informação.
