O StockFlow começou como um projeto acadêmico: uma aplicação local para controle de produtos, estoque e movimentações. Depois da entrega, decidi não tratá-lo como um projeto encerrado.

A partir daí, comecei a investigar o que seria necessário para transformar uma aplicação funcional em um sistema mais confiável, documentado e preparado para ser apresentado publicamente.

De entrega acadêmica a projeto público

A primeira versão cumpria seu objetivo acadêmico. O sistema permitia cadastrar produtos, registrar entradas e saídas, controlar usuários e aplicar regras de negócio relacionadas ao estoque.

Porém, executar uma aplicação localmente para uma avaliação é diferente de disponibilizá-la como parte de um portfólio profissional.

Para fazer essa transição, precisei olhar para o projeto como um sistema completo: código, banco de dados, segurança, testes, configuração, documentação e experiência de quem acessaria a aplicação.

O problema do ambiente

Na versão original, o sistema utilizava SQLite, uma escolha adequada para desenvolvimento local e para o contexto acadêmico. Para uma aplicação publicada, porém, eu precisava separar melhor as configurações de desenvolvimento e produção.

A configuração passou a escolher o banco a partir de variáveis de ambiente. Assim, o projeto continuou utilizando SQLite localmente, enquanto o ambiente publicado passou a utilizar PostgreSQL.

Essa mudança também deixou o projeto mais reproduzível. As informações sensíveis não precisavam estar no código, e cada ambiente poderia utilizar sua própria configuração.

Quando funcionar não era suficiente

Um sistema pode funcionar durante uma demonstração e ainda assim apresentar riscos quando submetido a outros cenários.

Por isso, revisei as regras de negócio relacionadas a produtos, usuários e movimentações. O sistema precisava impedir situações como estoque negativo, quantidades inválidas, produtos inativos sendo movimentados e perfis de usuário incompatíveis.

Também substituí mensagens soltas de terminal por logging estruturado, criando uma forma mais clara de acompanhar eventos importantes da aplicação.

Confiabilidade não é apenas o sistema funcionar no cenário esperado. É também saber como ele reage quando algo sai do esperado.

Segurança e controle de acesso

A evolução também exigiu revisar aspectos de segurança que não eram o foco principal da primeira entrega.

As senhas passaram a ser armazenadas por meio de hash, e as rotas foram protegidas de acordo com o perfil do usuário. Operações administrativas ficaram restritas a usuários autorizados.

Também foram considerados mecanismos de proteção para formulários, controle de sessão e tratamento de acessos não autorizados.

Para permitir que visitantes conhecessem o sistema publicado, criei um perfil de demonstração com permissões somente de leitura. Assim, qualquer pessoa pode navegar pelas telas sem comprometer os dados do ambiente de produção.

Do SQLite ao PostgreSQL

O banco PostgreSQL foi provisionado no Neon, enquanto a aplicação foi publicada no Render utilizando Gunicorn como servidor WSGI de produção.

Essa etapa revelou problemas que não apareciam no ambiente local: diferenças de configuração, conexão com banco remoto, variáveis de ambiente e necessidade de preparar o schema corretamente.

O deploy deixou de ser apenas o último passo. Ele passou a fazer parte do próprio processo de desenvolvimento e validação.

O papel dos testes

Os testes foram importantes para verificar se as melhorias de segurança e infraestrutura não quebravam as regras de negócio que já funcionavam.

Ao final da evolução, o projeto contava com 58 testes automatizados cobrindo serviços, produtos, usuários, movimentações e proteção contra requisições inválidas.

Além dos testes locais, configurei workflows no GitHub Actions para executar validações automaticamente, auditar dependências e verificar o comportamento da aplicação após o deploy.

resultado

Os testes transformaram mudanças arriscadas em mudanças verificáveis.

Uma demonstração pública

Depois da publicação, o StockFlow deixou de depender apenas de uma explicação ou de capturas de tela. O projeto passou a ter uma URL pública, documentação técnica, código versionado e um ambiente que pode ser explorado por visitantes.

O perfil de demonstração foi criado para equilibrar transparência e segurança. A pessoa visitante pode conhecer o dashboard, os produtos, as movimentações e a organização do sistema sem possuir permissões para alterar os dados publicados.

Essa decisão também tornou a experiência mais próxima de um produto real: quem acessa consegue entender o fluxo da aplicação sem precisar receber acesso administrativo.

O aprendizado

O StockFlow me mostrou que evoluir um projeto não significa apenas adicionar funcionalidades. É necessário pensar em configuração por ambiente, integridade dos dados, segurança, testabilidade, observabilidade, deploy e documentação.

A transformação mais importante não foi trocar SQLite por PostgreSQL ou publicar a aplicação no Render. Foi mudar a forma de enxergar o sistema: de uma entrega concluída para um produto que precisa ser compreendido, executado e avaliado por outras pessoas.

Os 58 testes representam mais do que um número. Eles representam uma tentativa de tornar cada evolução mais segura, observável e confiável.
